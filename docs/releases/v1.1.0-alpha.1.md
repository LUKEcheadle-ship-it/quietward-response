# QuietWard Response v1.1.0-alpha.1

Status: **candidate — automated and browser qualification required before tag/publication**

Backend/API version: `1.1.0a1`

## Purpose

This alpha turns Response from a narrow controlled-action demonstration into a broader incident-response workspace while preserving the original security boundary around endpoint execution.

The release is standalone. It does not require changes to any detector repository.

## New in this alpha

### Structured incident response plans

Every incident exposes:

`GET /api/v1/incidents/{incident_id}/response-plan`

Plans can cover:

- malware and suspicious files;
- process execution and privilege escalation;
- identity/authentication compromise;
- persistence;
- suspicious network activity;
- container compromise;
- vulnerabilities and configuration weaknesses;
- sensor/evidence integrity;
- operational failures that may overlap security events.

Each plan contains priority, attack families, objectives, investigation steps, containment steps, recovery steps, escalation conditions, limitations, and an exact executable-action list.

### Broader sensor vocabulary

The response-family mapper recognizes both canonical event types and common vendor/sensor terminology, including ransomware/trojan signals, brute force and credential spray, credential dumping, C2/beaconing, exfiltration/lateral movement, scheduled-task/autorun/service persistence, container/Kubernetes security alerts, CVE/misconfiguration findings, tamper/defense-evasion/sensor-health events, suspicious execution, file-integrity changes, and service/resource outages.

The response-plan API uses this same shared classifier. Static, API-level, and live-gate fixtures cover high-signal vendor names so classifier/plan drift cannot silently downgrade them to `unknown`.

### Analyst UI

Incident pages now show a dedicated Response Plan panel. Step labels make capability state explicit:

- `Available guidance`
- `Manual`
- `Planned · not executable`
- `Blocked · future capability`
- `Executable · approval required`

The controlled-action panel remains separate from advisory guidance.

### Bundled Response-owned alpha agent

The repository now includes `scripts/response_agent.py` and `scripts/enroll_response_agent.py`.

The alpha agent:

- polls outward using HMAC-authenticated requests;
- independently validates target agent/host, action type, parameters, policy allowance, lifecycle state, approval metadata, timestamps, and expiry;
- persists local execution intent and a terminal-result ledger;
- applies the demo fixture exactly once across retry/crash-recovery paths;
- sends signed executing/terminal results;
- has no subprocess/shell/PowerShell/cmd/service/process/firewall/quarantine/account/container/package execution primitive.

The enrollment helper writes the one-time agent secret to a private local JSON config and does not print it. The release audit rejects common agent credential/config filenames if they are accidentally tracked.

### ActionResult hardening

Before persistence:

- result payload maximum: 256 KiB serialized;
- evidence payload maximum: 64 KiB serialized;
- existing bounded error text remains in force.

## Executable surface

The alpha action registry still contains exactly one action:

`restart_quietward_demo_service`

The name is retained for v1 API compatibility. It is a demo-fixture capability, not a general service manager, and accepts no arbitrary target or command parameters. The bundled Response agent maps it only to its own dedicated JSON demo fixture.

The following are **not executable yet**, even though Response can produce a plan for them:

- process termination;
- file quarantine/deletion;
- firewall/network blocking;
- host isolation;
- container stop;
- persistence modification;
- session revocation/account lock;
- general service control;
- package/configuration mutation.

Those capabilities are future extensions of the bundled Response agent. Each requires its own narrow typed executor, endpoint-validated resource identity, preconditions, expiry, approval/policy binding, timeout/failure semantics, durable idempotency, rollback/containment metadata, least privilege, and adversarial qualification.

## Verification

Static/local candidate gate:

```text
python scripts/verify_v11_alpha.py
```

Standalone live HTTP gate:

```text
python scripts/verify_v11_alpha_live.py
```

The live gate covers canonical and vendor-style response-family mapping, rejection of non-registered advisory action names, the exact demo-only registry, approval/policy, Response-owned agent polling, exactly-once demo execution, signed result persistence, terminal replay, and audit-chain verification.

Exact-branch wrapper:

```text
python scripts/finalize_v11_alpha.py
```

Then complete the browser smoke in `docs/V11_ALPHA_ACCEPTANCE.md` on the exact candidate SHA.

## Known limitations

- analyst identity is still development-grade `X-Actor-ID`;
- production sensor adapters need source-specific authentication/trust contracts;
- HMAC agent transport requires TLS outside loopback/trusted development;
- the alpha agent stores its local-development credential in a permission-hardened JSON file rather than OS secret storage;
- audit chaining is tamper-evident rather than immutable;
- single-process/single-worker is the qualified API runtime;
- real containment remains manual/planned until additional narrow Response-agent executors are implemented and qualified.

## Safety statement

This alpha does not add arbitrary shell, PowerShell, cmd, bash, generic command execution, autonomous remediation, or LLM-generated executable commands.
