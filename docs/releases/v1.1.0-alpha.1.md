# QuietWard Response v1.1.0-alpha.1

Status: **candidate — automated and browser qualification required before tag/publication**

Backend/API version: `1.1.0a1`

## Purpose

This alpha turns Response from a narrow controlled-action demonstration into a broader incident-response workspace while preserving the original security boundary around endpoint execution.

The release is standalone. It does not require changes to any detector repository.

## New in this alpha

### Structured incident response plans

Every incident exposes:

`GET /api/v1/incidents/{incident_id}/response-plan`

Plans can cover:

- malware and suspicious files;
- process execution and privilege escalation;
- identity/authentication compromise;
- persistence;
- suspicious network activity;
- container compromise;
- vulnerabilities and configuration weaknesses;
- sensor/evidence integrity;
- operational failures that may overlap security events.

Each plan contains priority, attack families, objectives, investigation steps, containment steps, recovery steps, escalation conditions, limitations, and an exact executable-action list.

### Broader sensor vocabulary

The response-family mapper recognizes both canonical event types and common vendor/sensor terminology, including ransomware/trojan signals, brute force and credential spray, C2/beaconing, scheduled-task/autorun persistence, container/Kubernetes security alerts, CVE/misconfiguration findings, tamper/sensor-health events, suspicious execution, file-integrity changes, and service/resource outages.

### Analyst UI

Incident pages now show a dedicated Response Plan panel. Step labels make capability state explicit:

- `Available guidance`
- `Manual`
- `Planned · not executable`
- `Blocked · future capability`
- `Executable · approval required`

The controlled-action panel remains separate from advisory guidance.

### ActionResult hardening

Before persistence:

- result payload maximum: 256 KiB serialized;
- evidence payload maximum: 64 KiB serialized;
- existing bounded error text remains in force.

## Executable surface

The alpha action registry still contains exactly one action:

`restart_quietward_demo_service`

This is the historical demo-fixture capability. It accepts no arbitrary target or command parameters.

The following are **not executable yet**, even though Response can produce a plan for them:

- process termination;
- file quarantine/deletion;
- firewall/network blocking;
- host isolation;
- container stop;
- persistence modification;
- session revocation/account lock;
- service control;
- package/configuration mutation.

Those capabilities belong to the future dedicated Response agent and require their own typed executor, resource identity, preconditions, rollback/failure behavior, and adversarial qualification.


Standalone live HTTP gate:

```text

```

Exact-branch wrapper:

```text
python scripts/finalize_v11_alpha.py
```

Then complete the browser smoke in `docs/V11_ALPHA_ACCEPTANCE.md` on the exact candidate SHA.

## Known limitations

- analyst identity is still development-grade `X-Actor-ID`;
- production sensor adapters need source-specific authentication/trust contracts;
- HMAC agent transport requires TLS outside loopback/trusted development;
- audit chaining is tamper-evident rather than immutable;
- single-process/single-worker is the qualified API runtime;
- most real containment remains manual/planned pending the Response agent layer.

## Safety statement

This alpha does not add arbitrary shell, PowerShell, cmd, bash, generic command execution, autonomous remediation, or LLM-generated executable commands.
