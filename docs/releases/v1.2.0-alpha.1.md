# QuietWard Response v1.2.0-alpha.1

Status: **candidate — Linux finalizer, Windows exact-SHA live gate and browser/installed-service smoke required before tag/publication**

Backend/API version: `1.2.0a1`

## Purpose

v1.2 turns the broad v1.1 response-planning platform into the first alpha with narrowly executable real containment, continuously running endpoint agents, a bounded privacy-preserving network investigation action, and an optional read-only bridge from the separate QuietWard product.

The release remains standalone. No Response client, action executor or adapter code is placed inside the QuietWard repository.

## Eight-action executable surface

All actions require analyst approval and deterministic policy:

- `restart_quietward_demo_service` — dedicated demo fixture only;
- `collect_host_diagnostic` — bounded read-only host/agent health;
- `collect_process_diagnostic` — bounded read-only process snapshot and local process handles on Linux/Windows;
- `collect_network_diagnostic` — Linux-only bounded read-only `/proc/net` snapshot with endpoint-local keyed remote-address pseudonyms and local socket handles;
- `terminate_process_by_handle` — opt-in exact process termination on qualified Windows/Linux hosts;
- `collect_file_diagnostic` — bounded managed-root file snapshot and local file handles on Linux/Windows;
- `quarantine_artifact_by_handle` — opt-in managed-file quarantine on Linux/Windows;
- `restore_quarantined_artifact_by_handle` — Linux/Windows rollback through the quarantine-created handle.

No high-impact file/process action is advertised merely because the OS family is unknown. Process termination on Linux is also withheld from signed enabled capabilities unless pidfd support is actually present.

## Stronger decision quality

The release-correction pass tightens when incidents merge and when destructive actions become available.

### Correlation

Events are no longer merged merely because they share a category. v1.2 correlation requires either:

- a shared concrete process/file/network/persistence indicator; or
- a compatible multi-stage attack transition where at least one event contains explicit high-signal evidence and the evidence reaches high/critical severity.

This keeps unrelated same-category observations in separate incidents while allowing explainable execution→network, identity→privilege, execution→persistence and similar attack-chain correlation when evidence supports it.

### High-impact recommendations

Read-only diagnostics remain broadly available when relevant, but mutation is more selective:

- `terminate_process_by_handle` requires high/critical privilege escalation or high/critical process execution with explicit high-signal evidence such as reverse shell, credential dumping/theft, process injection, web shell, document→interpreter or ransomware-impact behavior;
- quarantine/restore requires malware-signature/YARA evidence, a high/critical newly created executable, or a high/critical file event with explicit known-bad-hash evidence;
- generic `process_start` and generic `file_change` no longer expose destructive actions in the normal analyst workflow.

The policy also fails closed when the target host record is missing. A stale/corrupt target host is rejected when an action is created and is independently rejected again during policy evaluation before dispatch.

## Continuous Response agent

Normal operation is now continuous:

```text
python scripts/poll_response_agent.py --config PATH_TO_AGENT_JSON
```

The agent refreshes its signed capability report before each poll, sleeps on a bounded interval, exits cleanly on SIGTERM/SIGINT and uses bounded exponential retry backoff when the control plane is unavailable. `--once` remains available for diagnostics/qualification.

User-scoped startup helpers are included:

- Linux: `scripts/install_response_agent_user_service.sh` + `deploy/quietward-response-agent.service`;
- Windows: `scripts/install_response_agent_windows.ps1`, which registers a limited current-user scheduled task.

The installed Linux and Windows runtimes include the canonical v1.2 private-state helper. Agent configuration, ledger, demo state, handle context and resource-handle state use bounded private state handling with randomized exclusive/no-follow atomic writes and verified no-follow reads. POSIX group/world-readable private state is rejected, and the writer syncs file data plus best-effort parent-directory metadata after atomic replacement.

The canonical runtime config loader fails closed on symlinked/non-private POSIX credential files. Windows installers reject reparse-point credential/runtime inputs. OS-backed secret storage remains a future hardening target.

## Separate QuietWard adapter

`scripts/forward_quietward_events.py` is maintained entirely in this Response repository.

It opens the QuietWard SQLite event database using `mode=ro` plus `PRAGMA query_only=ON`, never imports the QuietWard Python package, never writes detector tables, refuses host-ID mismatch, maps QuietWard event IDs deterministically to retry-safe UUIDv5 Response IDs, preserves assessment severity and privacy-bounded evidence, and sends `source=quietward` through a derived **event-ingestion-only HMAC subkey**. That subkey is accepted for event ingestion but is explicitly rejected for action polling.

The adapter keeps only its own private delivery cursor in the Response agent state directory. The adapter credential and cursor use the shared hardened private-state reader/writer. A server `duplicate_event_id` response is treated as already durable; an event-ID conflict fails closed.

Always-on user-scoped installers are included for Linux and Windows:

- `scripts/install_quietward_adapter_user_service.sh`
- `scripts/install_quietward_adapter_windows.ps1`

Both installed adapter runtimes include the hardened private-state helper. The combined workflow therefore remains **two separate repositories/products connected by a Response-owned read-only adapter**.

## Network diagnostic safety

`collect_network_diagnostic` is intentionally investigation-only.

It:

- accepts no server-supplied network target;
- reads `/proc/net/{tcp,tcp6,udp,udp6}` directly with no shell/subprocess execution;
- returns at most 256 rows and reports truncation;
- exposes protocol/family, local/remote scope, ports, connection state, an endpoint-local HMAC-SHA256 pseudonym for a concrete remote address when applicable, and an opaque local socket handle;
- keeps the 32-byte pseudonym key only in the agent state directory;
- validates that the state directory/key are normal private local objects, rejects link/reparse-like key paths and uses bounded no-follow verified key reads;
- keeps raw local/remote IP addresses, UID and inode inside the agent-local resource identity;
- returns `raw_network_addresses_returned=false` and `remote_address_identity=endpoint_local_hmac_sha256_128`;
- blocks release if the endpoint-local pseudonym key is accidentally tracked as a repository artifact;
- performs no firewall modification or host isolation.

The keyed pseudonym allows repeat-destination correlation on one endpoint without publishing a plain digest of low-entropy IPv4 addresses to the control plane.

## Signed endpoint capability negotiation

Agents sign supported and locally enabled action sets to:

`POST /api/v1/agents/{agent_id}/capabilities`

The report attests `arbitrary_command_execution=false` and the `qwrh1` handle protocol. Unknown capabilities are rejected.

Policy refuses non-demo actions when the report is missing, older than 15 minutes, implausibly future-dated, or does not enable the exact action. Enrollment, continuous polling and key-rotation paths use the canonical v1.2 agent capability set.

## Two-phase agent credential rotation

Rotation uses prepare → activate:

1. current credential signs `rotate-key`;
2. Response creates a five-minute pending credential while current remains active;
3. helper writes the pending secret to a private `.next` file;
4. pending credential signs `activate-key`;
5. activation promotes it and immediately revokes the old credential for normal HMAC traffic;
6. helper proves the promoted key with capability sync and atomically promotes `.next` using the hardened private-state writer.

Use:

```text
python scripts/rotate_response_agent_key.py --config PATH_TO_AGENT_JSON
```

Recover interrupted staging/activation with:

```text
python scripts/rotate_response_agent_key.py --config PATH_TO_AGENT_JSON --recover-next
```

After activation the old key cannot prepare another rotation or authenticate normal polling/result/capability traffic. Retired HMAC key material is not stored after activation and secrets are not printed.

## Resource identity model

The server does not choose raw process IDs or filesystem paths. The agent observes local state and creates random opaque `qwrh1_...` handles backed by private local identity/fingerprint records.

Handles are local, incident/host/agent-bound, expiring, single-consumption for mutating operations, and revalidated immediately before mutation.

Process termination/quarantine action TTLs are capped at 240 seconds, below the five-minute diagnostic handle lifetime.

## File safety and bounded work

File containment is restricted to configured managed roots. Symlinks are excluded. File identity includes metadata plus SHA-256 content. Quarantine revalidates before and verifies after the move, returns a rollback handle, and restore refuses occupied/escaped/tampered targets.

The read-only file diagnostic keeps the existing 64 MiB per-file limit and adds a **256 MiB total hashing budget per action**. Results report scanned bytes, the configured action budget, budget-skipped files and explicit truncation.

The documented remaining limitation is the narrow same-user filesystem race between final verification and a portable cross-platform move.

## Process safety

The executor protects the Response agent, parent, low/system PIDs and critical Windows process names. Identity includes creation/start data beyond PID. Linux uses pidfd-bound signaling where available/qualified and verifies exit; Windows revalidates process creation identity and performs a bounded exit wait. Stale/replaced identities and indeterminate interrupted outcomes fail closed.

## Analyst authentication

Loopback development retains the local actor-header convenience. Non-loopback/non-development Response requires hashed bearer credentials through `QWR_ANALYST_CREDENTIALS` with viewer/responder/admin roles. Authenticated bearer identity controls audit attribution and cannot be replaced by a spoofed `X-Actor-ID`. Remote analyst deployments require TLS/reverse-proxy transport protection; plain remote HTTP bearer transport is not an approved boundary.

## Signed audit checkpoints

v1.2 can export/verify HMAC-signed audit checkpoints at:

- `GET /api/v1/audit/checkpoint`
- `POST /api/v1/audit/checkpoint/verify`

The independent signing secret must be replaced outside loopback development using `QWR_AUDIT_CHECKPOINT_SECRET`. Externally retained checkpoints detect ordinary chain tamper, full historical recomputation after the checkpoint, deletion of already-checkpointed history, and checkpoint signature tamper.

A trusted audit checkpoint may be supplied at startup using `QWR_TRUSTED_AUDIT_CHECKPOINT_PATH` so a known retained historical prefix must verify before the service becomes available. The checkpoint input itself must be a bounded normal file: symlink/reparse-like, oversized, group/world-writable POSIX, or identity-changing files are rejected before signature/prefix verification.

This strengthens tamper evidence but is not immutable/WORM external logging.

## Security boundary clarifications

- Sensitive-field protection in v1.2 is **redaction, not database encryption**.
- The activated rotation schema has **no retired HMAC-key-material column**.
- The **integrity trust freeze** blocks medium/high/critical host mutation when an incident contains explicit sensor/evidence-integrity compromise; read-only investigation remains available.
- Signed endpoint capability negotiation and the trusted audit checkpoint are independent fail-closed controls and do not convert response-plan prose into executable commands.
- `/health` reports `response_scope=typed_controlled_response_v12`; generic/arbitrary remediation remains disabled.

## Abuse resistance and trust boundaries

- bounded API request size and per-client rate limit;
- bounded ActionResult/evidence payloads;
- security/no-store response headers;
- short high-impact TTLs;
- trusted same-incident/agent handle selection in the UI;
- endpoint capability freshness checks;
- integrity/tamper incidents freeze medium/high/critical state-changing response actions;
- sensitive credential-like fields are redacted before persistence.

## Still intentionally unavailable

- generic shell/PowerShell/cmd/bash/script execution;
- raw PID/path/network-target actions;
- firewall/network-rule changes or host isolation;
- account/session mutation;
- persistence mutation;
- container stop/remove;
- general service control;
- package/configuration mutation;
- autonomous or model-generated remediation.

## Qualification

The release requires two native execution gates on the **same exact candidate SHA**.

### Linux

Run on native Linux with `/proc/net`:

```text
python scripts/finalize_v12_alpha.py
```

The finalizer intentionally refuses non-Linux hosts. It requires full backend/static/local qualification, migrations, frontend build/audit, release-correction contracts, capability-aware live Linux process/file containment, the Linux privacy-preserving network diagnostic gate, and an isolated schema-compatible QuietWard SQLite read-only adapter → authenticated Response incident gate.

### Windows

Run on native Windows against the same SHA:

```text
python scripts/verify_v12_windows_live.py
```

This gate exercises the canonical v1.2 Windows capability set, server-side Windows OS policy, disposable process diagnosis/exact termination, disposable managed-file quarantine/rollback, raw target rejection, generic-command rejection and terminal replay/audit behavior.

Then complete every item in `docs/V12_ALPHA_ACCEPTANCE.md`, including Linux user-systemd startup, Windows limited-current-user task startup, browser/RBAC/key-rotation/audit smoke, and a Response-owned adapter smoke against the actually installed released QuietWard `v0.5.0-alpha.1` database on the XPS while proving QuietWard state remains unchanged by Response.

See `docs/V12_RELEASE_CORRECTIONS.md` and `docs/V12_RELEASE_CHECKLIST.md` for the post-review correction/evidence requirements.

The alpha must not be tagged/published unless every required gate passes on the same final SHA.
