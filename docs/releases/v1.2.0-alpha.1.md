# QuietWard Response v1.2.0-alpha.1

Status: **candidate — automated finalizer and browser smoke required before tag/publication**

Backend/API version: `1.2.0a1`

## Purpose

v1.2 turns the broad v1.1 response-planning platform into the first alpha with narrowly executable real containment plus a bounded privacy-preserving network investigation action, while preserving a fail-closed control plane.

The release remains standalone and does not require or modify any detector repository.

## Eight-action executable surface

All actions require analyst approval and deterministic policy:

- `restart_quietward_demo_service` — dedicated demo fixture only;
- `collect_host_diagnostic` — bounded read-only host/agent health;
- `collect_process_diagnostic` — bounded read-only process snapshot and local process handles;
- `collect_network_diagnostic` — Linux-only bounded read-only `/proc/net` snapshot with endpoint-local keyed remote-address pseudonyms and local socket handles;
- `terminate_process_by_handle` — opt-in exact process termination on Windows/Linux;
- `collect_file_diagnostic` — bounded managed-root file snapshot and local file handles;
- `quarantine_artifact_by_handle` — opt-in managed-file quarantine;
- `restore_quarantined_artifact_by_handle` — rollback through the quarantine-created handle.

## Network diagnostic safety

`collect_network_diagnostic` is intentionally investigation-only.

It:

- accepts no server-supplied network target;
- reads `/proc/net/{tcp,tcp6,udp,udp6}` directly with no shell/subprocess execution;
- returns at most 256 rows and reports truncation;
- exposes protocol/family, local/remote scope, ports, connection state, an endpoint-local HMAC-SHA256 pseudonym for a concrete remote address when applicable, and an opaque local socket handle;
- keeps the 32-byte pseudonym key only in the agent state directory with private POSIX permissions where supported;
- keeps raw local/remote IP addresses, UID and inode inside the agent-local resource identity;
- returns `raw_network_addresses_returned=false` and `remote_address_identity=endpoint_local_hmac_sha256_128`;
- blocks release if the endpoint-local pseudonym key is accidentally tracked as a repository artifact;
- performs no firewall modification or host isolation.

The keyed pseudonym allows repeat-destination correlation on one endpoint without publishing a plain digest of low-entropy IPv4 addresses to the control plane.

## Signed endpoint capability negotiation

Agents sign supported and locally enabled action sets to:

`POST /api/v1/agents/{agent_id}/capabilities`

The report attests `arbitrary_command_execution=false` and the `qwrh1` handle protocol. Unknown capabilities are rejected.

Policy refuses non-demo actions when the report is missing, older than 15 minutes, implausibly future-dated, or does not enable the exact action. The official enrollment, polling and key-rotation paths all use the same v1.2 agent capability set.

The normal capability-aware poll path is:

```text
python scripts/poll_response_agent.py --config PATH_TO_AGENT_JSON
```

## Two-phase agent credential rotation

Rotation uses prepare → activate:

1. current credential signs `rotate-key`;
2. Response creates a five-minute pending credential while current remains active;
3. helper writes the pending secret to a private `.next` file;
4. pending credential signs `activate-key`;
5. activation promotes it and immediately revokes the old credential for normal HMAC traffic;
6. helper proves the promoted key with capability sync and atomically promotes `.next`.

Use:

```text
python scripts/rotate_response_agent_key.py --config PATH_TO_AGENT_JSON
```

Recover interrupted staging/activation with:

```text
python scripts/rotate_response_agent_key.py --config PATH_TO_AGENT_JSON --recover-next
```

After activation the old key cannot prepare another rotation or authenticate normal polling/result/capability traffic. Retired HMAC key material is not stored after activation and secrets are not printed.

## Resource identity model

The server does not choose raw process IDs or filesystem paths. The agent observes local state and creates random opaque `qwrh1_...` handles backed by private local identity/fingerprint records.

Handles are local, incident/host/agent-bound, expiring, single-consumption for mutating operations, and revalidated immediately before mutation.

Process termination/quarantine action TTLs are capped at 240 seconds, below the five-minute diagnostic handle lifetime.

## File safety

File containment is restricted to configured managed roots. Symlinks are excluded. File identity includes metadata plus SHA-256 content. Quarantine revalidates before and verifies after the move, returns a rollback handle, and restore refuses occupied/or escaped/tampered targets.

The documented remaining limitation is the narrow same-user filesystem race between final verification and a portable cross-platform move.

## Process safety

The executor protects the Response agent, parent, low/system PIDs and critical Windows process names. Identity includes creation/start data beyond PID. Linux uses pidfd-bound signaling where qualified and verifies exit; Windows revalidates process creation identity and performs a bounded exit wait. Stale/replaced identities and indeterminate interrupted outcomes fail closed.

## Analyst authentication

Loopback development retains the local actor-header convenience. Non-loopback/non-development Response requires hashed bearer credentials through `QWR_ANALYST_CREDENTIALS` with viewer/responder/admin roles. Authenticated bearer identity controls audit attribution and cannot be replaced by a spoofed `X-Actor-ID`.

## Signed audit checkpoints

v1.2 can export/verify HMAC-signed audit checkpoints at:

- `GET /api/v1/audit/checkpoint`
- `POST /api/v1/audit/checkpoint/verify`

The independent signing secret must be replaced outside loopback development using `QWR_AUDIT_CHECKPOINT_SECRET`. Externally retained checkpoints detect ordinary chain tamper, full historical recomputation after the checkpoint, deletion of already-checkpointed history, and checkpoint signature tamper.

A trusted audit checkpoint may be supplied at startup using `QWR_TRUSTED_AUDIT_CHECKPOINT_PATH` so a known retained historical prefix must verify before the service becomes available.

This strengthens tamper evidence but is not immutable/WORM external logging.

## Security boundary clarifications

- Sensitive-field protection in v1.2 is **redaction, not database encryption**. Full encrypted evidence fields remain future work.
- The activated rotation schema has **no retired HMAC-key-material column**. Previous secret key material is not persisted after activation.
- The **integrity trust freeze** blocks medium/high/critical host mutation when an incident contains explicit sensor/evidence-integrity compromise; read-only investigation remains available.
- Signed endpoint capability negotiation and the trusted audit checkpoint are independent fail-closed controls and do not convert response-plan prose into executable commands.

## Abuse resistance and trust boundaries

- bounded API request size and per-client rate limit;
- bounded ActionResult/evidence payloads;
- security/no-store response headers;
- short high-impact TTLs;
- trusted same-incident/agent handle selection in the UI;
- endpoint capability freshness checks;
- integrity/tamper incidents freeze medium/high/critical state-changing response actions;
- sensitive credential-like fields are redacted before persistence.

## Still intentionally unavailable

- generic shell/PowerShell/cmd/bash/script execution;
- raw PID/path/network-target actions;
- firewall/network-rule changes or host isolation;
- account/session mutation;
- persistence mutation;
- container stop/remove;
- general service control;
- package/configuration mutation;
- autonomous or model-generated remediation.
